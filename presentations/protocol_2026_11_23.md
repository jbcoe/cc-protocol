# Polymorphism

Polymorphism (from the Greek for "many forms") is the ability of different objects to respond to the same function call in their own specific ways.

C++ supports polymorphism at compile time and at runtime.

---

# Compile-time polymorphism

Overloaded functions and function templates allow the compiler to determine which function to call during compilation:

```c++
double func(const A& a);
double func(const B& b);
```

```c++
template <typename T>
double func(const T& t);
```

The rest of this presentation is about runtime polymorphism.

---

# Closed-set runtime polymorphism

In C++ we can use `std::variant` and `std::visit` to implement closed-set polymorphism: runtime dispatch for a predefined set of types.

```c++
template <typename... Ts>
struct overload : Ts... {
  using Ts::operator()...;
};
```

```c++
std::variant<A, B, C> my_object;

std::visit(overload{[](const A&) { /* ... */ },
                    [](const B&) { /* ... */ },
                    [](const C&) { /* ... */ }},
           my_object);
```

---

# Open-set runtime polymorphism

A derived class can override member functions of a base class.

We can use the `virtual` keyword to require runtime resolution of a function.

A derived-class member function can then be called from a base class pointer or reference.

```c++
class Shape {
 public:
  virtual int sides() const = 0;
};
```

---

# Open-set runtime polymorphism (continued)

Derived classes inherit from `Shape` and override `sides()`:

```c++
struct Square : Shape {
  int sides() const override { return 4; }
};

struct Triangle : Shape {
  int sides() const override { return 3; }
};
```

---

# Manual dynamic dispatch

We can implement our own form of runtime dispatch using a function pointer.

```c++
class Square {
 public:
  int sides() const { return 4; }
};
```

```c++
class ShapePtr {
  const void* data_;
  int (*sides_func_)(const void* data);
  // ...
```

---

# Manual dynamic dispatch (continued)

The constructor of `ShapePtr` sets the function pointer to a function that calls `sides()` on the object `data_` points to.

```c++
 public:
  template <typename T>
  ShapePtr(const T* t)
      : data_(t), sides_func_(+[](const void* data) -> int {
          return static_cast<const T*>(data)->sides();
        }) {}

  int sides() const { return sides_func_(data_); }
};
```

---

# Manual dynamic dispatch (continued)

`ShapePtr` is a wide pointer, a data pointer with function pointers stored alongside it.

As defined, a wide pointer increases in size for each member function we add:

```c++
class WidePtr {
  const void* data_;
  int (*func_0_)(const void*, int);
  double (*func_1_)(const void*, double);
  // ...
};
```

Like many problems in computer science, we can solve this with another layer of indirection.

---

# Manual dynamic dispatch with a vtable

```c++
struct vtable {
  int (*func_0_)(const void*, int);
  double (*func_1_)(const void*, double);
  // ...
};
```

```c++
class WidePtr {
  const void* data_;
  const vtable* vtable_;
 public:
  template <typename T> WidePtr(const T* t);
  int func_0(int) const;
  double func_1(double) const;
};
```

---

# Construction of the vtable

For each type `T` the vtable pointer points to a compile-time static vtable instance.

```c++
template <typename T>
WidePtr::WidePtr(const T* t) : data_(t) {
  static constexpr vtable vtable_for_type = {
    .func_0_ =
      +[](const void* data, int a) {
        return static_cast<const T*>(data)->func_0(a);
      },
    // ...
  };
  vtable_ = &vtable_for_type;
}
```

The wide pointer does not manage the vtable lifetime.

---

# Dynamic dispatch with a vtable

The wide pointer is now two pointers in size regardless of how many functions it supports.

Member functions are dispatched through the vtable:

```c++
int WidePtr::func_0(int a) const {
  return vtable_->func_0_(data_, a);
}

double WidePtr::func_1(double a) const {
  return vtable_->func_1_(data_, a);
}
```

---

# Non-intrusive polymorphism with type erasure

The runtime polymorphism we've defined with our manual vtable does not require member functions to have been annotated with `virtual` keywords or for types to inherit from a base class.

The concrete type is "erased"; all necessary information is stored in the vtable.

A vtable can also be used for intrusive polymorphism, where the type itself holds the vtable pointer.

---

# Manual intrusive runtime polymorphism

```c++
class Shape;
struct vtable {
  int (*sides_)(const Shape*);
  // ...
};

class Shape {
 protected:
  const vtable* vtable_;
 public:
  int sides() const {
    return vtable_->sides_(this);
  }
};
```

Deciding which functions go into the vtable is akin to marking functions `virtual`.

---

# Manual intrusive runtime polymorphism (continued)

Our derived type defines a vtable and implements the necessary function(s):

```c++
class Square : public Shape {
 public:
  Square() {
    static constexpr vtable vtable_for_type = {
      .sides_ = +[](const Shape* shape) {
        return static_cast<const Square*>(shape)->sides();
      }
    };
    vtable_ = &vtable_for_type;
  }
  int sides() const { return 4; }
};
```

---

# Manual intrusive runtime polymorphism (continued)

Calls through `Shape` reach `Square::sides` via the vtable.

```c++
Square sq;
Shape& s = sq;
s.sides();
```

---

# Runtime polymorphism in Rust

Rust also supports runtime polymorphism with traits:

```rust
trait Shape {
    fn sides(&self) -> i32;
}
```

```rust
struct Square;

impl Shape for Square {
    fn sides(&self) -> i32 {
        return 4;
    }
}
```

---

# Implementing traits for types

In Rust, a trait can be implemented for a type in the crate that defines the type, or in the crate that defines the trait without changing the type.

In both cases runtime polymorphism is implemented using a wide pointer.

```rust
fn count_sides(shape: &dyn Shape) -> i32 {
    return shape.sides();
}
```

The size of `&dyn Shape` is twice the size of `&Square`.

---

# Polymorphism in Python

Python looks up a method by name when it is called.

We have duck-type polymorphism: if the name can be found, it can be used.

Static type checkers such as pyrefly support duck-typing with `typing.Protocol`:

```python
from typing import Protocol

class Shape(Protocol):
    def sides(self) -> int: ...
```

A function can use a `Protocol` to say which methods its argument needs:

```python
def count_sides(s: Shape) -> int:
    return s.sides()
```

---

# Existing libraries for duck-type polymorphism in C++

Boost.TypeErasure, Dyno and `folly::Poly` implement duck-type polymorphism in C++.

Each library declares interfaces with its own macros or templates, for example in Dyno:

```c++
DYNO_INTERFACE(Shape, (sides, int() const));
```

---

# Existing libraries for duck-type polymorphism in C++ (continued)

Without the macro, Dyno interfaces require explicit requirements and a concept map:

```c++
struct Shape : decltype(dyno::requires_(
  "sides"_s = dyno::method<int() const>
)) {};

template <typename T>
auto const dyno::default_concept_map<Shape, T> = dyno::make_concept_map(
  "sides"_s = [](const T& self) { return self.sides(); }
);
```

---

# Duck-type polymorphism in the C++ Standard Library

`std::function`, `std::move_only_function`, `std::copyable_function` and `std::function_ref` support a single call signature:

```c++
int count_sides(std::function_ref<int()> shape) { return shape(); }

struct Square {
  int operator()() const { return 4; }
};

Square sq;
count_sides(sq);
count_sides([] { return 3; });
```

---

# `std::polymorphic` from the C++26 working draft

`std::polymorphic<T, A>` (P3019R14, C++26) is an allocator-aware, owning value type for polymorphic objects.

```c++
std::polymorphic<Shape> s(std::in_place_type<Square>);
std::polymorphic<Shape> copy = s;  // deep copy
copy->sides();
```

---

# An early proposal for C++: `protocol` and `protocol_view`

P4148R2 proposes `protocol<I, A>`, an owning value type with allocator `A`, and `protocol_view<I>`, a non-owning view.

Any type that declares matching member functions can be used:

```c++
struct Shape {
  int sides() const;
};

struct Square {
  int sides() const { return 4; }
};
```

---

# An early proposal for C++: `protocol` and `protocol_view` (continued)

`count_sides` accepts any type conforming to `Shape` via `protocol_view`:

```c++
int count_sides(protocol_view<const Shape> s) {
  return s.sides();
}

Square sq;
count_sides(sq);
```

---

# Structural subtyping and conformance

A type conforms to an interface if it declares each of the interface's member functions with the same name and signature:

```c++
struct Shape {
  int sides() const;
};

struct Square {
  int sides() const noexcept;
  double area() const;
};
```

---

# Constructing a `protocol`

`protocol` has no default constructor. It can be constructed from a conforming value, in place, or by copy/move (when `I` allows it):

```c++
protocol<Shape> a(Square{});                       // from value (explicit)
protocol<Shape> b(std::in_place_type<Polygon>, 5); // in place
protocol<Shape> c(a);                              // copy (if I is copyable)
protocol<Shape> d(std::move(a));                   // move (noexcept)
```

---

# Allocator-extended constructors for `protocol`

Every `protocol` constructor has a corresponding allocator-extended overload:

```c++
using P = protocol<Shape, Alloc>;

P a(std::allocator_arg, alloc, Square{});
P b(std::allocator_arg, alloc, std::in_place_type<Polygon>, 5);
P c(std::allocator_arg, alloc, a);
P d(std::allocator_arg, alloc, std::move(a));
```

---

# Constructing a `protocol_view`

A `protocol_view` can be implicitly constructed from a conforming lvalue, a `protocol`, or (for a `const` view) a mutable `protocol_view`:

```c++
Square sq;
protocol<Shape> p(Square{});

protocol_view<Shape> v1 = sq;        // from non-const lvalue
protocol_view<Shape> v2 = p;         // from protocol
protocol_view<const Shape> cv1 = sq; // const view from lvalue
protocol_view<const Shape> cv2 = p;  // const view from protocol
protocol_view<const Shape> cv3 = v1; // const view from mutable view
```

---

# Member function forwarding

`protocol<I>` and `protocol_view<I>` forward `I`'s public non-static member functions directly, with deep `const` on `protocol` and shallow `const` on `protocol_view`:

```c++
struct Counter {
  int value() const;
  void increment();
};

const protocol<Counter> p(MyCounter{});
p.value();
// p.increment();  // ill-formed

protocol_view<const Counter> v = p;
v.value();
```

---

# Allocation-free move construction and a valueless state

Move construction takes the owned object from the source, so `protocol(protocol&&)` never allocates.

A moved-from `protocol` is in a valueless state:

```c++
protocol<Shape> p(Square{});
protocol<Shape> q(std::move(p));
assert(valueless_after_move(p));
p.sides();  // precondition violation
```

A moved-from `std::polymorphic` (P3019R14, C++26) is also valueless.

---

# Example: Pass an overload set with `protocol_view`

We can use `protocol_view` to define an improved `function_ref`:

```c++
struct Printer {
  void operator()(int) const;
  void operator()(std::string_view) const;
};

void print_all(protocol_view<const Printer> printer) { printer(42); printer("hello"); }

struct ConsolePrinter {
  void operator()(int i) const { std::println("int: {}", i); }
  void operator()(std::string_view s) const { std::println("text: {}", s); }
};

ConsolePrinter printer;
print_all(printer);
```

# Design for change

A later standard can allow code that is currently rejected, but cannot reject code that is currently allowed without breaking it.

We have chosen the simplest design and the most restrictive rules:

- Interfaces are plain structs, using no new syntax.
- Conformance needs an exact signature match.
- There is no conversion between `protocol`s of different interfaces.

# Appendix: Implementing `protocol` and `protocol_view` with reflection

Our reference implementation is informed by Ryan Keane's [`rjk::duck`](https://ryanjk5.github.io/posts/rjk-duck/).

It uses C++26 reflection (P2996) and builds with GCC and `-freflection`.

---

# Appendix: Generating a vtable with reflection

A simplified generator for named, non-overloaded functions.

Inspect `T` with `members_of` and define `vtable` with `define_aggregate`:

```c++
template <typename T>
struct vtable_generator {
  struct vtable;
  consteval {
    std::vector<std::meta::info> entries;
    for (auto m : members_of(^^T, std::meta::access_context::unprivileged()))
      if (is_function(m) && has_identifier(m))
        entries.push_back(vtable_entry(m));
    define_aggregate(^^vtable, entries);
  }
};
```

---

# Appendix: Generating a vtable with reflection (continued)

`vtable_entry` builds a function-pointer data member specification for one interface function:

```c++
template <typename R, typename... Args>
using entry_t = R (*)(const void*, Args...);

consteval std::meta::info vtable_entry(std::meta::info m) {
  std::vector args{return_type_of(m)};
  for (auto p : parameters_of(m))
    args.push_back(type_of(p));
  return data_member_spec(substitute(^^entry_t, args),
                          {.name = identifier_of(m)});
}
```

---

# Appendix: Limits of reflection

C++26 reflection focuses on inspection and simple type synthesis rather than general code generation.

`define_aggregate` can define a class's data members, but cannot generate member functions.

Without generated member functions, we need another way to give `protocol` and `protocol_view` member-call syntax.

---

# Appendix: Named callable member data

Each interface function becomes an empty data member with a call operator:

```c++
struct Sides { int operator()() const; };
struct SidesBase { [[no_unique_address]] Sides sides; };

struct protocol_view_Shape : SidesBase {
  const void* object_;
  const vtable_generator<Shape>::vtable* vtable_;
};

static_assert(sizeof(protocol_view_Shape) == 2 * sizeof(void*));
```

Each name gets its own base class, so the member sits at offset zero of that base class.

---

# Appendix: Vanishing `this`

Inside `Sides::operator()`, `this` points to the empty member `sides`. Two casts recover the enclosing object:

```c++
int Sides::operator()() const {
  auto* base = reinterpret_cast<const SidesBase*>(this);
  auto* self = static_cast<const protocol_view_Shape*>(base);
  return self->vtable_->sides(self->object_);
}
```

Two objects are pointer-interconvertible if "one is a standard-layout class object and the other is the first non-static data member of that object" ([basic.compound]/7).

# Appendix: Before C++26 reflection
